# Rollback operacional — Fase 5 (deploy Fases 1-4)

Backup de referência: `/home/pedro/vtres60-blog-deploy-backup-20260711T170351Z/`
Manifest: `deploy-manifest.json` no mesmo diretório.

## Quando executar

Qualquer uma das condições abaixo (ver Seção 23 do spec da Fase 5):

- `vtres60-blog` não inicia após o restart;
- home (`/blog`) retorna 500;
- `/blog/noticias` retorna 500;
- erro de módulo nativo (`sharp`) impede o startup;
- erro de import/build não detectado antes do restart;
- erro generalizado de Supabase no frontend (401, coluna inexistente);
- restart loop no PM2 (`restart_time` incrementando continuamente).

## Rollback de CÓDIGO (não mexe em dados/migrations)

Executar nesta ordem exata:

```bash
BACKUP_DIR=/home/pedro/vtres60-blog-deploy-backup-20260711T170351Z
cd /home/pedro/vtres60-blog

# 1. Parar worker
pm2 stop vtres60-agent-worker

# 2. Parar blog
pm2 stop vtres60-blog

# 3. Restaurar .next do backup
rm -rf .next
cp -a "$BACKUP_DIR/next-build" .next

# 4. Restaurar package.json/package-lock.json SE a instalação de dependências
#    tiver sido a causa suspeita (normalmente não é necessário nesta fase,
#    já que sharp já estava resolvido no lockfile anterior)
cp -a "$BACKUP_DIR/package.json" "$BACKUP_DIR/package-lock.json" .
npm ci

# 5. Restaurar arquivos de configuração se necessário
#    (normalmente ecosystem.config.js e agent-worker.mjs não mudam neste
#    deploy — restaurar apenas se algo nesta fase os alterou)
cp -a "$BACKUP_DIR/ecosystem.config.js" "$BACKUP_DIR/agent-worker.mjs" .

# 6. Reiniciar SOMENTE o blog com o build anterior
pm2 restart vtres60-blog

# 7. Validar
curl -sS -o /dev/null -w "home: %{http_code}\n" http://127.0.0.1:3002/blog
curl -sS -o /dev/null -w "noticias: %{http_code}\n" http://127.0.0.1:3002/blog/noticias

# 8. Manter o worker PARADO até nova investigação e aprovação explícita
#    para reiniciar (não reiniciar vtres60-agent-worker automaticamente).
```

## O que o rollback de código NÃO faz (intencionalmente)

- **Não remove** as colunas `image_source_url`, `image_credit`, `image_origin`,
  `image_hash`, `image_width`, `image_height` de `public.posts`. São
  aditivas e nullable — não quebram o código antigo, que simplesmente as
  ignora.
- **Não remove** o bucket `editorial-images` nem suas policies.
- **Não reverte** as migrations SQL aplicadas.

Motivo: uma vez que a nova pipeline gravar qualquer dado real nessas
colunas/bucket, uma reversão automática de schema arriscaria apagar dados
legítimos. Reversão de schema/Storage, se algum dia necessária, deve ser
uma decisão manual e explícita, feita separadamente — nunca parte de um
rollback automático de código.

## Rollback do worker (cenário: blog OK, agente com problema)

Se o blog novo funcionar mas o smoke test do agente (dry-run) ou o
comportamento pós-restart do worker falhar:

1. Manter `vtres60-blog` no build novo (não fazer rollback do blog).
2. Manter `vtres60-agent-worker` **parado**.
3. Não tentar reverter o worker sozinho para o código antigo sem revisar
   o `ecosystem.config.js` (ele aponta para o mesmo `agent-worker.mjs` —
   reverter exigiria também reverter `src/lib/agent/**`, o que
   re-introduziria os problemas das Fases 1-4 no restante do sistema).
4. Reportar `AGENT_DEPLOY_BLOCKED` e aguardar decisão explícita.
