### Incidente real durante o deploy (encontrado e corrigido, não escondido)

`pm2 restart vtres60-blog --update-env` usa o ambiente do **shell que executa o comando**, não o bloco `env` definido em `ecosystem.config.js`. O shell desta sessão tinha `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`/`SUPABASE_ANON_KEY` (sem prefixo `NEXT_PUBLIC_`) herdados de uma configuração de outro projeto Supabase — o mesmo tipo de bug já documentado em fases anteriores (`project_vtres60_pm2_env_fix.md`), mas atingindo o processo PM2 real desta vez, não apenas um servidor de teste isolado.

**Efeito real:** por alguns minutos, `/noticias`, `/agenda`, `/empresas/[slug]` e `/radar` retornaram HTTP 500 ("Error: Invalid API key") em produção. `vtres60`/`v360-dashboard` não foram afetados.

**Correção:** `pm2 restart ecosystem.config.js --only vtres60-blog --update-env`, que força a releitura real de `.env.production` (o mecanismo que `ecosystem.config.js` já foi desenhado para garantir, mas que só funciona quando o restart referencia o arquivo de config, não apenas o nome do processo). Confirmado via smoke test real: todas as páginas voltaram a 200, sem erros novos nos logs subsequentes.

**Lição para futuras fases:** `pm2 restart <nome-do-processo> --update-env` sozinho não é suficiente neste ambiente — sempre usar `pm2 restart ecosystem.config.js --only <nome> --update-env` para garantir que o `.env.production` correto seja injetado.
